# Delm 双代理协作与 Harness² 调优框架：运行时集成、可靠交付与验证

作者：陶壮（Zhuang Tao）

版本：2026-11-02

用途：学术与工程交流；本文是独立的 Agent 系统技术专题

## 摘要

自主编码代理能够调用工具并修改项目，但多代理执行还需要解决任务归属、结果交换、文件冲突、运行停滞与交付核验等系统问题。与此同时，提示词、技能、工具指南和协作规则共同影响执行行为，单次人工调整难以形成可重复的比较。本文介绍两项相关工程工作：将上游 Delm 的双 worker 看板协作语义适配到进程内 Agent 运行时，以及将上游 Harness² 的配置搜索与真实 rollout 调优流程接入同一运行时。

第一项工作通过追加事件日志、任务认领、增量视图和按需读取文件正文，使两个 worker 在结构化看板上协调。第二项工作建立 Python 调优器与 Node 执行器之间的版本化契约，使配置变体能够物化为可执行环境，并保留轨迹、产物、选择结果和人工采纳记录。实现进一步区分“执行正常结束”“出现工作证据”“产生候选交付物”和“交付物通过任务验证”，避免把运行状态误作质量结论。

截至本版，离线核验支持看板状态机、配置物化、runner 契约、轨迹渲染及部分任务适配机制。完整 Python 回归仍有旧接口用例与当前实现不一致，双代理会话测试受缺失 SDK 依赖阻断。本文保留这些限制，不据此宣称端到端性能提升、任务成功率提高或调优结果必然优于基线。

## 1. 工作范围与贡献边界

### 1.1 本文研究的系统问题

本文围绕两个层次展开：

| 层次 | 研究问题 | 工程对象 |
|---|---|---|
| 协作执行 | 两个自主 worker 如何分工、交换发现并可观察地结束任务 | Delm 看板语义、MCP 工具、双 worker 会话 |
| 配置调优 | 如何公平运行多个 harness 变体、核验产物并保留选择依据 | Harness² adapter、substrate、runner、结果管理 |

这里的 **harness** 指约束 Agent 执行的提示词、规则、工具指南、技能、脚本、子代理定义和钩子等配置组合。它不等于模型权重，也不代表训练基础模型。**rollout** 指给定任务输入、配置与预算后的一次真实代理执行。一次 **sweep** 则组织基线运行、变体提案、执行和选择。

Delm 和 Harness² 均有上游方法或实现来源。本文沿用源码中的 Delm 名称，不自行扩写其缩写，不将双 worker 协作协议或 Harness² 搜索算法整体宣称为本文作者原创。上游 Harness² 代码携带 Apache-2.0 许可；本文没有重新发布该代码，也没有替上游或原项目设定新的许可。

## 2. Delm 适配：将协作变成可回放的状态机

### 2.1 场景与现有方式的限制

两个 worker 处理同一代码任务时，如果只依赖自然语言聊天，容易重复做同一工作、误判对方进度，或在不知道版本关系的情况下覆盖文件。即便能相互发消息，也不等于拥有明确的任务归属与可追溯结果。

实现采用“共享看板协调、各自工具执行”的方式。worker-A 获得初始拆分任务的角色提示，worker-B 从看板读取并认领开放工作。两者共享项目工作区；任务归属、发现与完成声明通过看板工具表达。角色提示提供分工约定，运行时代码负责认领和完成权限等可执行约束。

### 2.2 模型与关键不变量

记看板事件流为

\[
L_t=(e_1,e_2,\ldots,e_t),\qquad
e_j=(\mathrm{seq}_j,\mathrm{actor}_j,\mathrm{kind}_j,\mathrm{payload}_j).
\]

任务队列状态由事件前缀回放得到：

\[
Q_t=\operatorname{Replay}(L_t),\qquad
q_i\in\{\mathrm{open},\mathrm{claimed},\mathrm{done}\}.
\]

`publish` 创建开放条目；`reserve` 创建并认领一个工作范围；`claim` 认领既有开放条目；`done` 关闭当前 worker 持有的条目。实现维持以下不变量：

1. 同一开放条目的认领先到先得，失败方得到当前 owner。
2. 每个 worker 同时最多持有一个未完成的 claim。
3. 只有拥有该 claim 的 worker 才能提交相应 `done`。
4. 对相同请求标识的完成或笔记重试保持幂等。

这些性质由本进程内同步状态更新实现。它们不构成跨进程分布式事务，也不证明两个 worker 的总体任务调度最优。

### 2.3 追加日志与增量视图

`DelmBoard` 保存事件流并派生任务、笔记、会话状态和文件元数据。首次读取返回完整视图；后续读取按各 worker 的读取游标返回新内容，未变化但仍活跃的任务压缩为身份、状态和 owner，减少重复上下文。

发现通过 `FACT` 或 `FAIL` 笔记表达。文件正文可以附着于完成声明或笔记；普通视图主要暴露文件名、大小和变化信息，需要时才 `expand` 读取正文或差异。由此把“协作状态可见”与“把所有文件始终塞入上下文”分开。

等待式读取由 `EventEmitter` 唤醒，事件到达时恢复等待者，且有等待上限。等待超时时不推进读取游标，避免尚未读取的信息在下一次调用中丢失。这是本地事件驱动机制，不需要持续访问外部看板服务。

日志可写入 JSONL，并在构造时回放。持久化实现采用 best-effort 写入，不能据此承诺掉电不丢事件、严格持久事务或无损恢复所有运行中工具调用。

### 2.4 MCP 身份绑定与文件应用保护

每个 worker 持有独立的看板 MCP server，actor 在创建时绑定到工具闭包，两个 server 共同操作同一看板对象。这样 claim、读取游标与发布者身份不依赖模型自行填写一个可信 actor 字段。

对通过看板传递的文件，`apply` 比较内容哈希与已知版本关系：

| 当前本地状态 | 处理 |
|---|---|
| 已与传入内容一致 | `unchanged` |
| 将应用的内容已被更新的 peer 版本取代 | `kept` |
| 文件缺失，或仍处于可安全替换的原始/已知版本 | `write` |
| 存在分歧的本地修改或不兼容的新版本 | `conflict`，拒绝该覆盖 |

保护范围是经由 `board.apply` 的文件交换。两个 worker 仍共享工作区，直接使用编辑工具修改同一路径时没有全局文件锁，不能把上述保护解释为所有文件写入均具备事务隔离。任务拆分、文件归属和最终测试仍然必要。

### 2.5 会话容器、派发与完成条件

`TeamSession` 组织两个 AgentSession、一个看板和各 worker 的事件流。当前代码中，首条用户任务输入会派发给所有 worker；后续用户追问由 lead worker 接收。任务队列派发也会广播给两个 worker。

对外仍保留单会话的事件接口；聚合事件带 worker 标识和团队级递增序号，便于显示、重新连接与分析。新开放任务出现时，空闲且未持有 claim 的 worker 可以被显式唤醒，弥补“没有在等待中的 SDK 调用就收不到看板通知”的情况。

正常完成要求看板已形成任务、所有条目均已关闭，且所有 worker 已结束当前回合。停滞检测按 worker 分别记录最近活动时间，避免活跃 worker 掩盖静默同伴。实现先提醒，超过独立的失败窗口后再报告失败；提醒持有 claim 的 worker 时优先要求完成收尾。

这里的“完成”是运行时状态条件，仍需独立验证代码或文档是否满足任务要求。声明完成、关闭条目或成功结束一个模型回合都不是功能正确性的充分条件。

## 3. Harness² 适配：让配置变体进入同一执行路径

### 3.1 问题建模与比较条件

令任务输入为 \(x\)，harness 配置树为 \(h\)，执行预算为 \(b\)，外部随机性为 \(\omega\)。执行产生轨迹 \(\tau\)、候选产物 \(a\) 和成本记录 \(c\)：

\[
(\tau,a,c)=\operatorname{Execute}(x,h,b;\omega).
\]

调优要比较的是配置对任务结果的影响。若输入 staging 不同、上次产物残留或各变体看到不同的任务基线，则差异不能归因于 harness。实现因此把输入快照、配置物化、运行目录、结果格式与产物判定作为显式接口。

这只是调优问题的表达，不表示当前实现已经求出某个期望质量函数的全局最优解。Agent 随机性、评审偏差和任务分布变化仍需实验控制。

### 3.2 搜索流程与候选范围

上游 Harness² 提供并行与顺序两种搜索组织方式，本文的贡献是运行时适配与可靠执行支撑。并行模式中，一项任务通常经历：

1. 运行 \(k\) 个基线 rollout，收集执行证据。
2. 基于共同证据提出 \(2k\) 个变体，分别属于 INV 和 DOM 两类修改方向，并执行这些变体。
3. 综合变体及其证据，生成 \(k\) 个 AGG 配置，再执行对应 rollout。
4. 匿名呈现符合条件的最终产物，保存选择结果和原因。

INV/DOM 分别对应通用执行行为与任务类型知识方面的修改方向；AGG 将不同修改方向的证据用于合成。源码另提供顺序模式，以逐步递归的方式构造最终候选。

一个容易混淆的边界是：当前并行模式最终选择池只包含 `agg1..aggk`，顺序模式包含 `c1..ck`；基线及中间变体不进入最终选择池，也没有基于基线的内建弃选。因此，“选中一个最终候选”不证明其优于基线。对外采纳前应另行比较基线与选中配置的独立任务验证结果。

### 3.3 Python 与 Node 的版本化执行契约

Python 调优器通过 substrate 调用 Node runner。接口承担任务输入目录、harness 目录、运行标识、输出目录、模式和超时等参数；结果以单行 JSON 写入 stdout，进度和诊断写入 stderr，避免将日志误解析为结果。

每次 rollout 留下可独立检查的文件：

| 文件或目录 | 作用 |
|---|---|
| `trajectory.txt` | 供调优器读取的标准化工具与代理轨迹 |
| `events.jsonl` | 执行器原始事件 |
| `workspace/` | 候选交付物快照 |
| `meta.json` | 模式、时间、预算、退出信息等元数据 |
| runner report | 本次执行、工具活动与产物判定的机器可读记录 |

退出码说明 runner 是否能正常完成调用；JSON 中的执行状态和产物字段说明 rollout 的不同侧面。成本无法获得时保留空值，不能用零代表未知成本。轨迹转换统一工具调用、观察、代理文本和错误的表示，并对截断规则进行回归核验。

### 3.4 配置物化与双 worker 接线

配置物化将通用 harness 树映射到运行时实际读取的位置：系统提示与规则、工具指南、声明式钩子、技能、子代理定义及脚本等。无法识别的组件应显式报告，避免配置“已搜索但从未生效”。

双 worker 模式增加三个可调面：worker-A 启动提示、worker-B 启动提示与看板指导。它们直接作为构造参数注入 TeamSession，再进入对应 worker 的提示组装。实际调用链为：

```text
任务与配置 -> Python sweep/substrate -> Node runner
           -> 读取双 worker 配置 -> TeamSession
           -> worker-A / worker-B -> 各自 MCP -> 共享 DelmBoard
           -> 轨迹与 workspace -> 最终候选选择 -> 人工检查与采纳
```

这条代码接线使两项工作形成实际关系：看板提供被调优的协作执行环境，Harness² 为该环境组织变体运行和证据比较。本文没有把整个 Agent 平台的其他引擎、市场或 RLM 扩展列为作者独立贡献。

## 4. 可靠交付：将容易混淆的四个判断拆开

### 4.1 输入完整性与 staging 缓存

任务运行需要足够完整的工程与数据输入；提案模型上下文则需要限制大小和可读类型。实现把两者的约束分开：staging 保留在配置额度内的任务文件，超出单文件或总量额度时记录跳过清单，并在诊断中说明；提交给提案或选择器的文本另行限制大小。

内联任务使用任务文本哈希区分 staging 目录，避免多个任务共用固定任务标识时错误复用第一份提示词。存储根目录允许配置，并优先采用持久数据卷，减少容器临时层容量对长任务的影响。

当前缓存键主要围绕任务文本构造，不能视为完整项目内容寻址。相同文字下项目文件更新是否会触发完整重建，需要结合实际 staging 状态检查；后续可以把源快照标识和输入清单纳入缓存键。

### 4.2 状态隔离与重跑基线

sweep 状态与 rollout 输出按用户、会话和命名空间组织，防止并发运行相互覆盖。运行标识在用于路径前检查字符和长度约束。

同一标识重跑时，执行器先检查运行目录仍在预期输出根目录内，再重新建立该次运行的工作区，避免上一轮残留文件被误判为新交付。需要续跑时，应将上一轮选定产物显式放入任务输入，再让各候选从同一 seed 出发，而不是各自继承不透明的残留。

### 4.3 执行、工作证据、产物、正确性

实现中的判断应按以下语义理解：

| 层次 | 当前判据或证据 | 能支持的结论 |
|---|---|---|
| 执行正常结束 | `ok`、退出状态和错误字段 | 执行器报告一次正常结束 |
| 存在可分析工作 | 有 rollout 记录，且正常结束、已产生候选产物或存在工具调用 | 可把执行证据交给后续分析 |
| 存在候选交付物 | 显式交付物路径，或相对 seed 新增/内容改变的文件 | 有值得检查的结果 |
| 任务验证通过 | 外部测试、独立构建、验收或人工复核 | 在指定验证范围内满足要求 |

因此，超时或停滞不一定意味着之前产生的文件毫无价值；但存在工具调用也不意味着交付成功。目录存在尤其不能证明运行开始，因为 substrate 可以在调用 runner 前就创建目录。

`rollout_ok` 使用“有运行记录，且 `ok` / `delivered` / 工具调用证据至少一项成立”的宽松标准，目的是保留可分析的执行。后续候选池仍要求相应的可读交付物。报告与演示不能把该字段直接翻译成任务正确率。

### 4.4 修改 seed 也是交付物

许多代码任务要求改进已有文件。如果产物提取只排除所有 seed 文件名，那么修改既有实现恰好会被漏报。实现改为比较内容：未变的 seed 不作为产物，新增文件或内容已变化的 seed 可以进入候选提取。

runner 一侧使用输入文件哈希判断变化，选择器适配一侧也按内容差异提取可读文件。元数据、harness 自身与依赖目录被排除，避免把内部记账当作用户产物。单独的哈希变化仍不证明语义改善，最终必须有任务验证。

### 4.5 结果检查、采纳与回收

结果管理提供配置差异检查、采纳、回滚与工作产物回收。配置采纳与回收 `workspace` 产物是两个不同动作：调优出一份有效配置不自动把候选代码写回用户项目。允许在外部检查选中运行后，再决定是否引入配置或代码。

这些管理能力形成可审查的工程闭环，但不会自动补足缺失的独立评测。当前任务源没有统一评分 rubric，不能从框架本身导出一个经校准的综合质量分数。

## 5. 本版验证与可支持的结论

### 5.1 验证方法

2026-11-02，在已提交源版本的独立副本中，以 Node.js 24.13.0、Python 3.14.3 运行无需真实模型连接的既有测试。没有启动线上服务、调用生产模型、改动原工作区或新增性能实验。

| 验证对象 | 实际结果 | 解释 |
|---|---|---|
| 看板生命周期、认领、增量视图、等待、幂等、文件保护 | 13 通过，0 失败 | 支持这些本地协议行为 |
| Harness² Node 物化、runner 契约、轨迹渲染 | 58 通过，0 失败 | 包含 dry-run；不等于真实模型端到端验证 |
| Python staging、输入键、产物检测、rollout 可用性与轨迹的定向类 | 35 通过 | 是下一行 84 项中的子集，不能重复累计 |
| Python 两个相关测试文件的完整发现 | 84 项中 58 通过、9 失败、12 错误、5 跳过 | 全量测试未通过 |

全量 Python 失败具有可追溯原因：部分用例仍以旧 `plan.json` 任务源为前提，而当前提交要求显式内联任务文本；旧产物 fixture 与当前 seed 读取位置不一致，也导致两条断言失败。它们是本版源码与测试的不一致，不能仅归因于测试环境。五条跳过的用例要求额外的 runner 仓库环境配置。

本版没有修改源仓库来消除这些失败，保留原始日志和返回码。通过的 35 项定向用例验证了相应新机制，但不能替代全量回归。

### 5.2 实验与业务效果边界

已提交修正与回归测试支持以下工程判断：任务输入应独立于模型上下文额度管理；可用运行不能仅看目录或退出状态；seed 修改需要内容比较；并发 sweep 要有作用域；停滞应按 worker 观察。

尚未建立可对外引用的多任务、固定预算、重复运行的单代理/双代理和调优前后对照。因此本文不报告吞吐提升、任务成功率提高、成本下降比例或压缩算法速度改善。原工作区另有未提交实验报告，本版未将其数值写入摘要或结论。

## 6. 学术解释与后续实验设计

### 6.1 协作收益需要扣除协调成本

若任务可分解为工作量 \(W_A,W_B\)，简单的两 worker 墙钟分解可写为

\[
T_2 \approx \max(W_A,W_B)+T_{\mathrm{coord}}+T_{\mathrm{merge}}+T_{\mathrm{verify}}.
\]

该式仅用于说明机制：并行减少可分部分的串行等待，协调、合并和验证会抵消收益。任务耦合强、claim 拆分不均或两个 worker 争用同一文件时，双代理可能更慢。当前实现不保证加速，也没有对真实任务验证上述近似的精确程度。

### 6.2 后续对照应固定任务、输入与预算

建议在可公开的任务集上比较单代理、默认双代理、调优双代理，统一模型版本、输入快照、可调用工具与预算。每项任务进行独立重复，分别统计：独立验收通过率、墙钟时间、模型用量、工具调用、冲突事件、重试、停滞和人工介入。

Harness² 实验还应单列基线、中间变体与最终选中候选的独立评分，报告无改进和退化案例；将调优任务与保留任务分开，检查配置是否只适用于单一任务。不要用候选自身写的总结替代测试，更不能把“由盲选器选中”当作泛化性能证明。

### 6.3 尚未解决的问题

主要限制包括共享文件系统上的直接编辑冲突、JSONL 的 best-effort 持久性、相同任务文字下输入更新的缓存失效、旧测试接口漂移、模型评审偏差和长运行的资源开销。运行时的自动权限、进程预算和外部工具边界还需要在部署环境中验证；本报告不将进程内看板当作完整安全隔离方案。

## 7. 可公开的技术成果表述

对外介绍可采用下述归因清晰的表述：

> 我负责 Delm 双 worker 协作能力及 Harness² 调优框架的运行时工程工作：将共享看板协调适配为进程内 MCP 工具与事件状态机，并打通配置变体、真实 Agent 执行、轨迹、候选产物和人工采纳。围绕长任务与并发运行，我实现或修正了任务输入 staging、状态隔离、产物内容检测和逐 worker 停滞处理。协作协议与搜索方法有明确的上游来源；现有离线回归支持部分机制，端到端性能与泛化收益仍待完整对照实验。
